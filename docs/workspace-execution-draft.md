# Kami 工作空间执行说明

状态：七项拆分、阻塞关系及本地 Markdown 方案已获用户确认，已发布为独立 tickets；01–06 已完成本地实施与复审，07 尚未实施。依据为已确认的工作空间设计收敛、术语表与 ADR 0001–0002；不重新讨论产品方向。

## 组织方式

每项交付一个可演示、可验证的完整行为，包含必要实现、回归检查和用户文档同步。保留现有组件，局部整理与对应行为一起完成，不安排独立的大重构或调查阶段。实现完成可独立合并；最终跨平台候选验收另设第 07 项，不替代每项自己的测试。

本轮以 Companion 作为跨仓库工作入口，采用本地 Markdown、一项一文件，状态为 `ready-for-agent`，阻塞关系决定是否可开始。跟踪约定见 [任务跟踪配置](agents/issue-tracker.md)。

完整清单与独立验收条件见 [执行项索引](../.scratch/kami-workspace/README.md)；后续状态和验收条件只在各 ticket 中维护，避免双份内容漂移。

## 执行规则与检查

初始可开始集合为 01、02、04、06；03 在 01 与 02 后开始，05 在 04 后开始，07 在全部行为项完成后开始。共用样式或调度代码的任务即使没有逻辑阻塞，也应串行落地或使用隔离分支，不能因文件重叠虚构产品依赖。

每项在自身完成时验证，不能把所有测试推迟到 07。主题使用 `npm ci` 和 `npm run check`；修改主题 CSS 后先运行 `npm run sync`。Companion 使用 `npm ci` 和 `npm run check`。候选视觉检查使用 `KAMI_VISUAL_THEME_CSS` 指向实际配套主题资产后运行 `npm run check:visual`；验收票必须把当前仅以 macOS 为正式依据的门禁更新为双平台要求。

实施预计跨两个仓库超过八个文件，主要变化限于现有呈现、生命周期、测试、生成产物和验收文档；无新服务、新账号、API key、网络运行时依赖或笔记迁移。原生菜单接入的具体官方 API 应在实施前按安装的 Obsidian 类型定义核对，不在 tickets 中冻结不稳定的选择器或代码路径。

主要风险是窗口级 Focus 与应用当前活动视图并非同一作用域，以及 CSS 继承可能让组件继续使用旧色板；分别用多窗口行为检查和最终计算样式检查约束。任何一票回退均只回退对应插件／主题改动，不触碰笔记；最终证据随候选资产变化重新验证。
